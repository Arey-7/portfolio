Portfolio: design system & wireframes

The reference for building aaronmulandi.com. Every value here maps to a Tailwind token. Build against this document rather than improvising, and the fourteen-day timeline holds.

01 — Direction

What this site is trying to say

A design direction is a constraint, not a mood board. Every decision below traces back to this one sentence.

"This person builds systems that hold up when the infrastructure doesn't."

Three principles

  • Instrument, not artwork. The visual language borrows from measurement equipment — monospace labels, hairline rules, readouts. It should feel like something that reports state, because that's what your work does.
  • One memorable thing. The traffic-shaping simulation in the hero is where the creative budget goes. Everything else stays quiet so it lands.
  • Density over emptiness. Engineers read. Generous whitespace with three words in it signals a designer's portfolio, not an engineer's. Aim for calm density.

What we're deliberately avoiding

  • Inter on near-black with a neon accent. The default dev-portfolio look. Instantly forgettable.
  • Terminal cosplay. Fake command prompts and blinking cursors read as costume. A real interactive simulation reads as competence.
  • Skill proficiency bars. "React 85%" is meaningless and every engineer knows it.
  • Scroll-jacking and heavy parallax. Costs performance, annoys anyone skimming.

Rules

  • Mono is for data, not decoration. Labels, metrics, stack chips, code. Never body prose.
  • One display weight per page section. Mixing 600 and 700 in adjacent headings looks accidental.
  • Negative tracking on display only. Body and mono stay at default; tightening small text hurts legibility.
  • Never centre a paragraph. Centre short headings if you must; never multi-line prose.

Build these once. Everything on the site composes from them. If you need an eighth, ask whether an existing one can stretch.

Buttons — two variants only Primary action Secondary

Solid amber for the single primary action per view. Outlined for everything else. Min height 44px on touch. No third variant.

06 — Wireframes

Page layouts

Structure only. Build these as grey boxes first, then apply the system above.

Home — desktop (1440px)

Asymmetric hero. Copy left, simulation right. The widget is above the fold on desktop — a visitor sees the interactive thing before they scroll.

Decisions

  • No hero image. You're an engineer, not a photographer. The simulation is the visual.
  • Project cards are split. Prose left, topology/stack right — the diagram gives engineers something to read that isn't marketing.
  • Three cards maximum on the homepage. More dilutes.
  • Nav has four items. Any more and nobody reads any of them.

Home — mobile (375px)

Everything stacks. Simulation drops below the CTA; project cards lose the side panel and put chips inline.

Mobile rules

  • Simulation stays interactive — don't replace it with a static image. It's the thing that works.
  • Nav collapses to a menu, or drop it entirely and rely on scroll. Four sections doesn't need a drawer.
  • Topology diagram scrolls horizontally rather than shrinking to unreadable.
  • Tap targets 44px minimum, including the toggle.

Project detail — /work/[slug]

Metrics row is mandatory. Three numbers, mono, above the prose. It's the first thing an engineer looks for and the thing most portfolios omit. Structure the body as problem → approach → result → what I'd do differently — that last section signals seniority more than anything else on the page.

07 — Motion

Interaction & motion

Motion earns its place by clarifying state. Anything decorative costs performance and attention.

InteractionSpec
Link / button hoverborder-color + color, 180ms ease
Scroll revealopacity 0→1, translateY 14px→0, 600ms ease, once only
Simulation barsrequestAnimationFrame, lerp factor 0.12
Toggle state changeinstant — state changes shouldn't be animated
Focus ring2px solid link, offset 3px, no transition
Page transitionnone

Every animation must respect prefers-reduced-motion. In the simulation this means snapping to the target value instead of easing. This is a fundamentals check a reviewer may actually run.

The non-negotiables

Semantics checklist

  • One <h1> per page; heading levels never skip
  • Real <nav>, <main>, <footer>, <article> — not divs with classes
  • Simulation toggle is a <button> with aria-pressed, wrapped in a labelled group
  • SVG wireframes and diagrams carry role="img" and aria-label
  • Full keyboard traversal with visible focus at every stop
  • Decorative images get alt="", never a missing attribute

Build order

  • Config first. Tokens before components, always.
  • Then the seven primitives in /components. Build them in isolation on a scratch route.
  • Then compose pages from primitives. If a page needs a one-off style, that's a signal the primitive is wrong.
  • Simulation last. It's the fun part — don't let it eat days one through three.
